# 改卡候选框架

本框架用于处理“我要做一张新卡”或“我要修改某张卡”的完整工作流。目标不是让 AI 成为最终裁判，而是让 AI 稳定地充当编辑助手：查询现状、指出风险、生成可复制候选文本、等待作者修改卡面，再把作者实际完成的最终文本同步到数据库和交付文件。

## 核心原则

- 作者意图优先。AI 可以反对、提醒、建议，但不能阻止生成候选文本。
- 候选层不是源数据。`data/change_candidates.json` 中的内容只有在作者确认并完成 PSD/Excel/数据库更新后，才会进入源数据层。
- TODO 是讨论和施工参考，不是最终数据来源。作者实际修改后的卡面文本具有最高优先级，即使它与 TODO 不完全一致。
- 评估和文本生成分开。即使 AI 认为修改有风险，也必须给出一个“按作者意图执行”的候选版本。
- 不要求一次评估完美。强度、定位、电子化风险等可以逐步积累到评语层。

## 标准输入

作者可以用自然语言提出：

```text
我想改周芷若，把九阴白骨爪输出提高 100，你看怎么样？
```

或：

```text
我要做某某人物，核心形象是……，大概想有两个招式和一个身份技。
```

也可以直接从已有 TODO 开始：

```text
我已经按改卡 TODO 修改了某某卡，请按实际卡面更新数据库并完成后续交付。
```

新开一个专门改卡的对话时，可以这样开场：

```text
请使用 $wuxia-card-change-flow。你的任务是做五行卡牌的新卡/改卡候选助手：
先查当前资料，不改源数据库；如果你不赞成我的想法，也要给出风险提示和按我意图写出的候选文本。
我接下来会告诉你要做或要改的卡。
```

Agent 应主动补齐以下信息：

- 目标：新卡还是改旧卡。
- 设计目标：增强、削弱、贴合艺术形象、统一文本、减少歧义等。
- 当前文本：如果是改旧卡，先查当前数据库和必要卡面。
- 作者硬要求：哪些内容必须保留，哪些可以调整。
- 未决问题：如果关键信息不足，列出需要作者裁定的问题。

## 流程入口

流程不要求每次从候选讨论开始。Agent 应判断当前进度并从最早尚未完成的一步继续：

- 没有候选：从讨论和候选文本开始。
- 已有 TODO、仍在讨论：读取候选，只继续未决问题。
- 已有 TODO、作者正在改卡：直接提供复制文本和排版说明。
- 作者已经改完卡面：直接读取实际卡面并进入回录，不重复评审。
- 数据已经同步但 TODO 尚未清除：先核验同步结果，再完成状态和交付。

按卡名匹配到多个有效候选时，必须确认具体候选 ID；只有一个明确候选时无需重复询问。恢复旧 TODO 时，还要重新读取当前数据库，不能假定数据库仍与候选创建时完全相同。

## 输出结构

每次改卡讨论至少输出：

- 当前理解：一句话说明作者要做什么。
- 简短评估：艺术形象、规则稳定、文本清晰、强度影响。
- AI 态度：`support`、`caution`、`oppose` 或 `uncertain`。
- 候选文本：按作者意图写出的完整文本或局部修改文本。
- 可直接复制粘贴：不夹带解释的纯净替换文本。
- 更新说明草稿：面向玩家的一两条说明。
- 待作者裁定：尚不能确定的问题。

## AI 反对时的处理

如果 AI 认为修改不好，必须分成两段：

1. **风险提示**：说明为什么可能不好。
2. **仍按作者意图生成候选**：给出可用文本。

不要只说“不建议”。本项目的目标是辅助作者落地，而不是替作者否决。

## 写入候选层

使用：

```powershell
python scripts/add_change_candidate.py <卡名> <作者请求> --ai-position caution --full-text "..."
```

常用字段：

- `--candidate-type revision`：修改旧卡。
- `--candidate-type new_card`：新增卡。
- `--design-goal`：设计目标。
- `--ai-position`：AI 态度。
- `--rationale`：修改理由。
- `--current-snapshot`：当前卡牌摘要。
- `--full-text`：候选完整文本。
- `--patch`：局部修改条目。
- `--patch-note`：玩家更新说明草稿。
- `--risk`：规则或强度风险。
- `--question`：待作者裁定问题。

## 状态流转

- `draft`：初稿。
- `needs_author_review`：已整理好，等作者看。
- `approved`：作者确认文本方向。
- `source_applied`：实际卡面已经回录并通过 Excel/SQLite/JSONL 核验，但作者仍在继续本批其他卡，最终 Excel 和更新日志尚未生成。
- `applied`：PSD、Excel、数据库、更新说明已同步完成。
- `rejected`：作者放弃。

## 作者确认与卡面施工

作者确认候选方向后：

1. 作者修改 PSD。
2. 候选保持 `approved`，仍显示在 `改卡TODO.md`。
3. 此时不得仅按候选内容提前更新源数据库。

## 作者完成卡面后的回录

作者告知卡面已修改后：

1. Agent 读取更新后的卡面，或取得作者提供的最终精确文本。
2. 对比旧数据库、TODO 候选和实际最终卡面。
3. 以实际最终卡面为准更新当前基准 Excel；最终文本可以与 TODO 不同。
4. 重建 SQLite 与 JSONL，并逐项核对 Excel、SQLite、JSONL 和最终卡面。
5. 根据实际旧文本到最终文本的差异生成更新日志，不得直接沿用候选日志。
6. 如果作者还要继续修改本批其他卡，将候选标记为 `source_applied`，记录批次编号、实际差异和所属牌堆；重新生成 `改卡TODO.md` 后，该项从可见 TODO 中消失。
7. 作者说明本批全部完成后，汇总本批全部 `source_applied` 项，生成并检查一份包含全部当前卡牌的 Excel、本批实际改动的更新日志，以及“哪些牌堆改了哪些卡”的结论，再统一标记为 `applied`。

在实际卡面、Excel、SQLite、JSONL 完全核对之前，候选文本不得视为当前牌面事实，候选也不得标记为 `source_applied` 或 `applied`。
