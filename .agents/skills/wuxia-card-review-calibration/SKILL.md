# 五行卡牌模块化评审校准

## 1. 默认加载

正式评价前完整读取：

- `docs/ai-understanding/core/game-flow.md`
- `docs/ai-understanding/core/combat-baseline.md`
- 当前卡牌对应的一个类别模块
- `docs/skills/wuxia-card-review-workcard.md`

不要整份读取旧规则总表、全部术语、全部案例、全部玩家动态或旧轮次AI评审。

## 2. 先按卡牌类别路由

### 战斗人物

唯一竞争两张战斗人物名额的类别。读取：

- `docs/ai-understanding/evaluation/card-types/combat-character.md`
- `docs/ai-understanding/evaluation/functions/README.md`
- 与主要功能相关的一至数个功能模块

必须判断主要功能、次要功能和保底功能，再选择同功能案例比较。

### 附加人物、物品、称号

这些卡摸到后直接进入本局，不需要在弃牌阶段竞争，也不占两张战斗人物名额。

分别读取对应类别模块，在“已经进入本局”的前提下评价它对本局的实际帮助。不得虚构携带槽位、获得成本、转移、覆盖、失去或其他未校准规则。

### 场景

场景定义整局环境。只评价整局流程变化、策略、规则稳定性和体验，不做普通强度评分。

## 3. 人机双向定性对齐先行流程 (Qualitative Alignment First)

在进行任何定量数学仿真、存活回合演算或评分前，必须严格执行以下对齐流程，严禁直接跨越进行数值期望与矩阵计算：

1. **规则与手牌机制核实**：检索卡牌数据库与基础规则。特别注意：**每个人物在战斗回合中拥有一整套 8 张基础手牌可供自主出牌选择**，技能启动判定是百分百可用的主动博弈抉择，非随机抽取。
2. **特技定性理解汇报**：向作者逐条列出该卡所有特技的定性理解，包括：触发时序与生效位置（正面/侧面）、主语语义、伤害类型（常规/一定造成/生命流失）、是否为叠加攻击等。
3. **暂停并核对**：**AI 必须暂停并等待作者的口头裁定与核对**。只有在作者明确确认所有特技定性理解“完全正确”后，AI 才能进入下一步定量计算，白白浪费 token 和脑补结论被绝对禁止。
4. **定量仿真与登记**：核对无误后，进行博弈期望、穿透率和等效正面存活回合数等数学仿真，登记至 `calibrated_stats.json`，并完成工作卡。
5. **严禁脑补，必须写清条件概率计算过程**：在定量仿真时，AI 严禁直接给出拍脑袋的估计值。如果计算中包含未知变量（如“敌方输出水平”），AI 必须：
   * **显式定义假设变量**（例如：“假定常规对阵敌方的名义招式输出 $A_{\text{敌，招式}}$ 为 700 点”）；
   * **进行严格的条件期望推导**：例如在一阳指成功释放的分支下，一灯的两个招式位必然未被克（期望伤害上升），而敌方在该分支下也必然未克制一灯（期望伤害下降），必须使用条件概率公式 $E[X | C]$ 计算两边的条件期望，不得使用无条件均值代替；
   * **保留计算全过程**：在最终的单卡 Markdown 笔记以及 `calibrated_stats.json` 中，必须清晰书写推导公式与参数来源，严禁只保留一个光秃秃的最终数字，防止后续 AI 使用结论时产生脑补或瞎蒙。

## 4. 战斗人物基础门槛


任何战斗人物必须先完成：

1. 白人四卡基础推演。
2. 白人期望输出400的基线核验。
3. 每项主动大招的位置、放法、放出率和失败下限。
4. 多项主动大招的位置竞争和同回合兼容性。
5. 单项增伤、减伤和反伤逐项结算。

主动大招默认要求放法中的每张卡均未被克且至少一张克敌（先天功等改写此规则的被动除外）。一张克敌、一张被克不能放出。

简单独立条件优先用概率公式。例如两张均不能被克的概率为`(4/5)²=16/25`，不以枚举代替简单计算。


## 5. 单卡证据接口

每张卡独立完成工作卡。必须保留：

- 事实与来源
- 作者校准原话
- 类别、进入本局方式和流程节点
- 主要、次要和保底功能（仅战斗人物）
- 逐技事实表
- 同卡组合与冲突
- 常态、失败和上限结算链
- 输出与爆发
- 正面生存
- 侧面生存
- 类别专属价值
- 优点
- 缺点
- 实际玩法
- 反证审计
- 规则风险
- 电子化风险
- 同功能比较锚点
- 可迁移结论
- 置信度和必要的待校准问题

非战斗类别没有独立承伤意义时，正面生存和侧面生存分别写“不适用”及原因，不得伪造战斗分数。

## 6. 规则、术语、案例和玩家动态

- 规则：通过`docs/ai-understanding/rules/README.md`按关键词定向读取。
- 术语：只查询`data/review/rule_terms.json`中的实际词条。
- 案例：只加载同类别、同主要功能、同关键机制的少量案例。
- 玩家动态：只在能力依赖玩家意愿、桌面政治或仇恨时定向读取。

历史AI评审、聚合平均分和旧类别画像只能作为待审材料，不能作为当前规则或作者锚点。

## 7. 比较与评分

- 先比较同主要功能，再比较次要功能。
- 对照实际结算时点、常态、下限、上限、频率、目标、穿透、失败条件和存活。
- 跨功能的正面输出差距不能直接推出整卡强弱。
- 分数必须有物理规则 and 横向锚点依据，并注明置信度。
- 关键规则未明且会改变结论时，暂不锁定。

## 8. 反证与锁定

初稿完成后检查：

- 最可能被高估和低估的能力。
- 是否把理论对象当成稳定触发。
- 是否把玩家心理当成牌面规则。
- 是否漏算位置竞争、次数、失败和结算时点。
- 是否因大数字、技能多或文字长而高估。

只有全部独立栏目通过后才能标记`locked`。不得由批量脚本或生成正文的同一步骤自动锁定。

## 9. 写入边界

- AI评价、攻略和风险不得进入源数据库。
- 作者反馈按内容进入核心规则、专项规则、术语、评价模块、案例、单卡理解或玩家动态；不得全部塞进术语层。
- 新规范只约束之后开始或作者要求返工的评审，不自动批量重写旧评审。
- 未经作者明确允许，不进行提交、推送或发布。
