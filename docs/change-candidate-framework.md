# 改卡候选框架

本框架用于处理“我要做一张新卡”或“我要修改某张卡”的工作流。目标不是让 AI 成为最终裁判，而是让 AI 稳定地充当编辑助手：查询现状、指出风险、生成候选文本，并把候选记录在可追踪的派生层。

## 核心原则

- 作者意图优先。AI 可以反对、提醒、建议，但不能阻止生成候选文本。
- 候选层不是源数据。`data/change_candidates.json` 中的内容只有在作者确认并完成 PSD/Excel/数据库更新后，才会进入源数据层。
- 评估和文本生成分开。即使 AI 认为修改有风险，也必须给出一个“按作者意图执行”的候选版本。
- 不要求一次评估完美。强度、定位、电子化风险等可以逐步积累到评语层。

## 标准输入

作者可以用自然语言提出：

```text
我想改周芷若，把九阴白骨爪输出提高 100，你看怎么样？
```

或：

```text
我要做某某人物，核心形象是……，大概想有两个招式和一个身份技。
```

新开一个专门改卡的对话时，可以这样开场：

```text
请使用 $wuxia-card-change-flow。你的任务是做五行卡牌的新卡/改卡候选助手：
先查当前资料，不改源数据库；如果你不赞成我的想法，也要给出风险提示和按我意图写出的候选文本。
我接下来会告诉你要做或要改的卡。
```

Agent 应主动补齐以下信息：

- 目标：新卡还是改旧卡。
- 设计目标：增强、削弱、贴合艺术形象、统一文本、减少歧义等。
- 当前文本：如果是改旧卡，先查当前数据库和必要卡面。
- 作者硬要求：哪些内容必须保留，哪些可以调整。
- 未决问题：如果关键信息不足，列出需要作者裁定的问题。

## 输出结构

每次改卡讨论至少输出：

- 当前理解：一句话说明作者要做什么。
- 简短评估：艺术形象、规则稳定、文本清晰、强度影响。
- AI 态度：`support`、`caution`、`oppose` 或 `uncertain`。
- 候选文本：按作者意图写出的完整文本或局部修改文本。
- 更新说明草稿：面向玩家的一两条说明。
- 待作者裁定：尚不能确定的问题。

## AI 反对时的处理

如果 AI 认为修改不好，必须分成两段：

1. **风险提示**：说明为什么可能不好。
2. **仍按作者意图生成候选**：给出可用文本。

不要只说“不建议”。本项目的目标是辅助作者落地，而不是替作者否决。

## 写入候选层

使用：

```powershell
python scripts/add_change_candidate.py <卡名> <作者请求> --ai-position caution --full-text "..."
```

常用字段：

- `--candidate-type revision`：修改旧卡。
- `--candidate-type new_card`：新增卡。
- `--design-goal`：设计目标。
- `--ai-position`：AI 态度。
- `--rationale`：修改理由。
- `--current-snapshot`：当前卡牌摘要。
- `--full-text`：候选完整文本。
- `--patch`：局部修改条目。
- `--patch-note`：玩家更新说明草稿。
- `--risk`：规则或强度风险。
- `--question`：待作者裁定问题。

## 状态流转

- `draft`：初稿。
- `needs_author_review`：已整理好，等作者看。
- `approved`：作者确认文本方向。
- `applied`：PSD、Excel、数据库、更新说明已同步完成。
- `rejected`：作者放弃。

## 确认后的工作

作者确认后才执行源数据流程：

1. 作者修改 PSD。
2. 更新 Excel。
3. 重建数据库。
4. 生成玩家更新说明。
5. 更新 release 卡面图。

在这些步骤完成前，候选文本不得视为当前牌面事实。
